# AI Provider Discovery & Recheck Agent — Technology & Architecture Plan

## Context

The project ("In Need of Time") helps people in crisis (single moms, people experiencing homelessness, people recently released from prison) find providers — health clinics, food banks, shelters, free-clothing programs, etc. Provider data lives in Sanity CMS. An in-progress package, `packages/agent-core`, already contains a partial AI harness (built on the OpenAI Agents SDK) that can crawl a provider's website and extract structured provider data via `runProviderPipeline`/`runProviderExtraction`. This work is uncommitted/in-progress on the `api` branch alongside a brand-new, mostly-empty NestJS app (`packages/api`).

The goal is to turn this into a real product feature with two entry points:

1. **Manual**: an editor pastes a URL into the `apps/ai-provider-editor` Sanity App SDK app; the agent extracts provider info and the editor reviews/edits before saving.
2. **Scheduled**: a per-provider cadence (weekly/monthly/etc.) triggers a recheck of each provider's known source URL(s). Detected changes are **never auto-applied** — they always go through human approval, surfaced via both an in-Studio review queue and an email digest.

This plan focuses on **what packages/technologies to introduce and where**, plus the minimum architecture needed to justify those choices and wire the two use cases into the existing `agent-core` pipeline (reusing it, not duplicating it).

- Delete the orphaned dead-code dir `packages/agent-core/src/providerExtractionAgent/` (singular; empty prompt, superseded by `src/agents/providerExtractionAgent/`).
- Fix prompt bug in `packages/agent-core/src/agents/providerExtractionAgent/prompt.ts`: `${getCurrentDate}` → `${getCurrentDate()}`.
- Standardize on the `firecrawl` npm package going forward (agent-core's choice) rather than perpetuating `frontend`'s separate `@mendable/firecrawl-js` client — plan to retire `frontend/lib/agent/*` and `frontend/app/api/agent/route.ts` once the new pipeline covers its functionality.

| Agent/LLM harness                    | Keep **`@openai/agents`** (already in use) — `runProviderPipeline` / `runProviderExtraction` in `packages/agent-core` | Already built and working; both use cases should call this same code, not parallel logic                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Web fetching/crawling                | Keep **`firecrawl`** (already in use)                                                                                 | Already integrated (`urlMapTool`); retire the duplicate `@mendable/firecrawl-js` client in `frontend`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Sanity read access from `agent-core` | Add **`@sanity/client`**                                                                                              | Needed for the real `getServiceTypesTool` query and for fetching a provider's current field values to diff against                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Job orchestration / cron             | **Inngest**                                                                                                           | The pipeline is multi-step and can be slow (crawl + several sequential LLM calls per URL, × N providers on a schedule) and needs **per-provider cadences**. Inngest gives cron triggers, event-driven fan-out (one durable run per due provider), and automatic per-step retry/checkpointing — all without provisioning new infrastructure (no Redis, no always-on server), so `packages/api` can stay serverless-friendly. Runner-up considered: Trigger.dev (also durable, but a separate deploy target); rejected as primary: raw Vercel Cron/QStash (no step-level checkpointing — a transient failure mid-pipeline forces a full redundant re-crawl) and a persistent NestJS+BullMQ setup (real ops burden — Redis + an always-on host — for a small team) |
| Email notifications                  | **Resend** (+ optionally `@react-email/components` for the digest template)                                           | First-class TS SDK, pairs naturally with the existing Vercel/Next.js stack, generous free tier for a low-volume nonprofit digest. Postmark is a solid fallback if deliverability ever becomes a concern                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| In-Studio review queue               | Native **Sanity Studio** — new document type + structure builder list + custom document actions                       | No new package needed; Sanity already is the database of record, and Studio's structure builder / document actions are exactly built for this pattern (the repo already has one example: `RunProviderAgentAction.tsx`)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Audit logging                        | Keep **Drizzle/Postgres** `agentAuditLogTable` (already exists)                                                       | Just needs `packages/api` to actually depend on `@in-need-of-time/db` and write to it (currently doesn't)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

## Where new logic lives

- **`packages/agent-core`** (pure logic, reused by both use cases, no HTTP/queue/email code):
  - `src/sanity/client.ts` — read-only `@sanity/client` instance.
  - `src/sanity/getProviderSnapshot.ts` — GROQ fetch of a provider's current fields.
  - `src/diff/diffProviderFields.ts` — pure function comparing current vs. freshly-extracted provider data → `{changedFields, patch}`.
- **`packages/api`** (NestJS — thin HTTP layer, holds write-capable Sanity token, owns email + job wiring):
  - `src/providers/` module — `POST /api/providers/discover` and `/extract`, wrapping `agent-core`'s pipeline + writing to `agentAuditLogTable` via a new `AuditService`.
  - `src/sanity/sanity-write-client.provider.ts` — the one place holding a Sanity write token; used only to create `pendingProviderChange` docs and patch `lastCheckedAt` — never to write provider content directly.
  - `src/notifications/email.service.ts` — Resend wrapper.
  - `src/inngest/functions/` — `recheckProvidersCron` (finds due providers, fans out one event per provider), `recheckSingleProvider` (crawl → extract → diff → create `pendingProviderChange` if changed → patch `lastCheckedAt` → audit log), `sendReviewDigestCron` (one daily digest email of pending items, not one email per item).
  - Add `@in-need-of-time/db` as a real dependency (currently missing) and a shared-secret auth guard reusing the existing `x-api-key` convention from `RunProviderAgentAction.tsx`.
- **`studio`** — schema + review UI only, no pipeline logic:
  - Add to `src/schemas/provider/baseProvider.ts` (shared by `provider` and `regionalProvider`): `sourceUrls` (array of url), `recheckCadence` (select: none/weekly/monthly/quarterly), `lastCheckedAt` (datetime, agent-written).
  - New document type `src/schemas/providerChange/pendingProviderChange.ts`: `provider` (reference), `sourceUrl`, `status` (pending/approved/rejected), `proposedData` (typed subfields mirroring provider fields, not raw JSON — so Studio renders it and it flows through `sanity typegen`), `changedFields` (string array), `auditLogId` (correlates to the Postgres row), `reviewedBy`/`reviewedAt`.
  - `src/structure/index.ts` — add a "Provider Review Queue" list filtered to `status == "pending"`.
  - New document actions `ApproveProviderChangeAction.tsx` / `RejectProviderChangeAction.tsx` (same pattern as existing `RunProviderAgentAction.tsx`). Approve writes to the provider's **draft** (not published) inside a `client.transaction()` alongside marking the change approved — so a human still has to hit Publish, a second safety net beyond the approval click itself.
- **`apps/ai-provider-editor`** — manual-flow UI only; calls `packages/api` over HTTP (it's a browser app — it must not import `agent-core` directly, which needs server secrets). On save, writes the reviewed/edited result **directly to Sanity as a draft** via `@sanity/sdk`, not back through the API — keeping `packages/api` write-token-free for this path.

## New packages, by location

- `packages/agent-core`: `@sanity/client`
- `packages/api`: `@in-need-of-time/db` (workspace dep), `@sanity/client`, `inngest`, `resend`, `@react-email/components` (optional), `serverless-http` (if deploying Nest to Vercel serverless, matching the rest of the stack)
- `studio`: `nanoid` (make explicit — currently relied on transitively)
- `apps/ai-provider-editor`: `@sanity/ui` / `@sanity/icons` (optional, cosmetic)
- `frontend`: no additions; plan to remove `openai` + `@mendable/firecrawl-js` once `frontend/lib/agent/*` is retired

New env vars: `SANITY_API_WRITE_TOKEN`, a consolidated shared-secret name (repo currently has `LOCAL_API_KEY`/`SANITY_STUDIO_LOCAL_API_KEY`/`NEXT_PUBLIC_LOCAL_API_KEY` sprawl — pick one), `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `INNGEST_EVENT_KEY`, `INNGEST_SIGNING_KEY`, `SANITY_APP_API_BASE_URL`, `SANITY_APP_API_SHARED_SECRET`.

## Verification

- `npm run -w @in-need-of-time/agent-core type-check` and `npm run -w @in-need-of-time/api` build after the prerequisite cleanup, to confirm the stale-import bug and stub tool are actually fixed.
- Locally run the Inngest dev server (`npx inngest-cli dev`) against `packages/api` to step through `recheckSingleProvider` for a single seeded test provider and confirm a `pendingProviderChange` doc appears in the local Sanity dataset with a sensible diff.
- Exercise the manual flow end-to-end in the browser: run `apps/ai-provider-editor` (`npm run app:ai-provider-editor`) and Studio side by side, paste a real provider URL, confirm extracted data renders, edit a field, save, and confirm a draft appears in Studio.
- Confirm the Approve action in Studio correctly creates/updates a draft (not the published doc) and that Reject leaves the provider untouched.
- Send a test digest email via Resend's sandbox/test mode before wiring the real cron schedule.
